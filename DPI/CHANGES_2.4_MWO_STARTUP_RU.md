# NoDPI DLM 2.4: MWO/CDN и диагностика WinDivert

Исходный патч поверх **2.3 Telegram**. В архив включены только изменённые и новые файлы. Готовых EXE, DLL, драйверов и пользовательских настроек в нём нет.

## Установка

1. Закройте NoDPIGui, NoDPI, NoDPIProbe и DPITrainer.
2. Содержимое папки `DPI` из архива скопируйте с заменой в `M:\users\Ark\Desktop\DLM\DPI`.
3. Запустите прежний `Build-And-Run.cmd`. Требуются DLM 0.133.0+ и x64 MinGW GCC; SDK по умолчанию находится в соседней `DLM-OUT`.
4. Для рабочего ПК с ошибкой запуска сначала запустите `Check-Driver.cmd` **от имени администратора**. Из GUI эта проверка открывается с UAC кнопкой «Проверить драйвер» после ошибки.
5. Запустите «Собрать отчёт» / `Collect-Diagnostics.cmd`. Если ошибка 58 осталась, пришлите новый ZIP: он содержит результаты двух проб драйвера и сведения Windows.

Старый `config.ini` не заменяется. Неудачный подбор не перезаписывает действующий профиль. Старые профили Schema=1 с Target=0…4 читаются с прежним значением цели.

## Что показал рабочий лог Windows 11

В `DPI-diagnostics-20261119-153526.zip`:

- исходная проверка HTTPS проходит **3/3**: Yandex, Mail и Wikipedia;
- в `NoDPI.log` ошибка **WinDivertOpen 58** повторяется 11 раз;
- `training.status`: elapsed=66, budget=600, generation=1, **tested=0**, message=`Candidate engine exited: 2`;
- активен USB Ethernet ASIX AX88179, интерфейс 34; одновременно присутствует маршрут отключённого Wi-Fi;
- в Telegram-пробах сохранён текст исключения контроллера об изменении сетевого окружения. Это не ответ серверов Telegram;
- SHA-256 локальных WinDivert.dll и WinDivert64.sys совпадают с исходным комплектом.

Таким образом, в последнем сеансе минуту заняла подготовка; ни один кандидат ещё не был проверен. Сообщение GUI о необходимости проверить соединение не описывало фактический сбой открытия движка.

**Точная причина Win32=58 этим архивом не установлена.** Этот код нельзя автоматически приравнять к отключённой BFE, блокировке подписи или несовпадению файлов драйвера. Отсутствие WinDivert в прежнем Get-Service также не доказывает отсутствия загруженного драйвера ядра.

## Исправление запуска и остановок обучения

Перед длительными сетевыми пробами выполняется `NoDPI.exe --driver-check --automatic` с текущим config.ini:

1. открывается минимальный фильтр `false`;
2. открывается рабочий фильтр в режиме **SNIFF | RECV_ONLY**;
3. оба дескриптора закрываются; обработка пакетов не запускается.

Эта проверка не блокирует и не переписывает трафик, не вызывает WinDivertRecv/Send. Сам WinDivert при открытии может штатно загрузить свой драйвер. Скрипты не меняют конфигурацию BFE, HVCI, антивируса или сетевых интерфейсов.

Если открытие не удалось, поиск завершается до измерения кандидатов. Сохраняются компонент, точный Win32-код, PID и признак готовности. При ошибке обычного движка записывается отдельное событие `startup_failure`, включая ошибки WinDivertOpen и настройки очереди. GUI различает подготовку, проверку драйвера, сетевые пробы и ошибку запуска.

Проверка неизменности сети теперь:

- использует активные адаптеры и подключённые IP-интерфейсы, в том числе VPN;
- учитывает предпочтительные исходящие адреса, активные маршруты, метрики и порядок DNS;
- сравнивает нормализованный набор, независимо от порядка выдачи Windows;
- не включает адреса и маршруты отключённых адаптеров и временные состояния DAD;
- записывает снимки «до» и «после изменения», затем останавливает сравнение.

Наличие отключённого Wi-Fi в старом логе не доказывает, что именно он вызвал прежнюю остановку: для этого нужны оба снимка. Исключения контроллера теперь выходят из TCP/WSS-проб Telegram как отмена всего испытания и не увеличивают число сетевых неудач Telegram.

**10 минут — верхний бюджет поиска.** Ошибка драйвера, отмена, смена сети, подтверждённый результат или доступность всех проб без обработки могут завершить его раньше. Работающий интернет без NoDPI не объявляется заслугой нового метода.

## MWO, Cloudflare, CloudFront и Azure

Добавлены:

- семейство `mwomercs.com`, включая `ac.mwomercs.com` и `static.mwomercs.com`;
- распознавание Cloudflare по официальным IPv4/IPv6 сетям;
- `cloudfront.net` и клиентские GLOBAL CLOUDFRONT сети AWS;
- `azurefd.net`, `azureedge.net`, `vo.msecnd.net` и клиентские сети AzureFrontDoor.Frontend;
- домены Azure Websites, Blob/Web Storage, CloudApp и Traffic Manager;
- определение владельца неизвестного TLS-соединения по фактическому TCP-кортежу Windows и имени MWOClient.exe / MWOPortal.exe.

Cloudflare, CloudFront и Microsoft Azure — разные инфраструктуры. Все сети AMAZON и AzureCloud не включаются в общий обработчик автоматически. Полный AzureCloud используется для классификации; неизвестное соединение обрабатывается при подтверждённом владельце MWO или подходящем домене. Имя процесса определяется через QueryFullProcessImageNameW; в журнал пишутся PID и вид клиента, без полного пути программы.

Для новых потоков MWO/CDN используются разрезы TCP, обратная отправка сегментов и перекрытие **теми же исходными байтами**. Поддельные TLS-пакеты, RST и порча контрольной суммы для этой ветви отключены. Существующие ветви YouTube, Discord и Telegram имеют приоритет и сохраняют прежнюю обработку. Локальные адреса, известные DNS/DoH-узлы и пользовательские исключения учитываются до обработки.

При отсутствии SNI IP-область применима только к известной CDN-сети или подтверждённому процессу MWO; при настроенных списках доменов такой поток пропускается. Неизвестные протоколы и игровой UDP этим патчем не переписываются.

Для поиска добавлены цели:

| Target | Область |
|---|---|
| 0 / 1 / 2 | YouTube / Discord / оба, как раньше |
| 3 | Telegram Web + Desktop |
| 4 | YouTube + Discord + Telegram, как в 2.3 |
| 5 | MWO + CDN |
| 6 | Все перечисленные сервисы |

В цели 5 поиск не тратит попытки на варианты поддельных пакетов: неиспользуемые поля генома нормализуются, одинаковые кандидаты внутри поколения объединяются. Профиль сохраняет параметры, контекст сети и CDN-списков, результаты публичных MWO-проб и явные `MwoAccountTested=0`, `MwoGameplayTested=0`.

Подготовка периодически проверяет обновления официальных списков, обычно раз в неделю. При ошибке загрузки сохраняется рабочий файл и остаётся встроенный снимок; следующая попытка — через 6 часов. Принудительная проверка — `Update-CDN-Ranges.cmd`; перезапустите движок после обновления. Списки проверяются целиком до замены: синтаксис CIDR, публичные адреса, канонические границы, минимальные размеры префикса и пределы объёма. Изменение выбранного файла во время обучения останавливает сравнение.

## Как проверить MWO

1. Включите обработку и заново запустите MWO, чтобы создались новые TCP-соединения.
2. Если нужно, выберите **MWO + CDN / Cloudflare / Azure** и запустите подбор. Старый режим «все три» остаётся целью 4, новый общий режим — «Все сервисы».
3. Запустите `Check-MWO.cmd`. Проверяются четыре публичных ресурса, с запросом HTTP/2 и отдельно HTTP/1.1: главная, форма входа, frontend ac и CSS-файл CDN. HTTP/2 может согласовать HTTP/1.1 — фактический протокол записывается в отчёт.
4. Затем в течение 90 секунд наблюдения выполните вход в клиенте игры. Для короткого отчёта без наблюдения: `Check-MWO.cmd -ObserveSeconds 0`.
5. Укажите фактический результат и точный код ошибки игры в MANUAL_RESULTS.txt, затем соберите диагностику.

`ac.mwomercs.com/login` сейчас возвращает штатный HTTPS redirect на `https://mwomercs.com/login`. Проба принимает только этот точный адрес с кодом 301/302/307/308 и помечает результат как доступность frontend. HTML формы входа проверяется по признакам MWO и полям email/password; challenge и HTTP 403 не засчитываются. CSS должен передать не меньше 32 КиБ, поэтому передача только первых 16 КиБ не становится успехом.

**Это не автоматический вход в игру.** Публичные HTTPS-пробы не подтверждают доступность всех закрытых серверов авторизации, матча, голосового чата или аккаунта. Не читаются пароли, cookies, tdata, содержимое браузерных профилей и тела игрового трафика. Сокеты в Check-MWO — только процессы MWOClient/MWOPortal; для UDP Windows отдаёт здесь лишь локальную конечную точку, не удалённый адрес. DNS-отчёт использует обычный системный резолвер.

В media-url.txt ничего для MWO, Telegram или CDN добавлять не требуется: это файл прямого URL видеопотока YouTube.

Разбиение TCP не создаёт новый маршрут. Если блокируется сам IP/соединение до TLS или сервер отклоняет регион на своей стороне, один такой обработчик не гарантирует доступ. Успех на вашем провайдере требуется проверить запуском игры; в этой среде его не было возможности измерить.

## Новые данные в диагностике

- logs/startup-PID.json и .status: результат запуска и Win32-код;
- logs/driver-preflight-*.json: ранняя проверка перед обучением;
- logs/driver-check-*.json: ручная проба драйвера;
- logs/driver-system-*.json и driver-system.json в ZIP: сборка Windows, BFE/mpssvc, драйверы ядра, хеши и подписи файлов, сведения Device Guard и доступные события CodeIntegrity/System, отфильтрованные по WinDivert/NoDPI;
- logs/network-context-*-before/changed.json: сравниваемые снимки сети;
- logs/probe-mwo-*.json, logs/mwo-check-*.json: HTTPS, DNS и соединения игры;
- события mwo_process_scope / cloud_cdn_scope: причина выбора области, провайдер и PID;
- выбранные встроенные/кэшированные CIDR-файлы с разными именами в ZIP, журнал обновления и версия сборки.

Ошибки чтения системных данных сохраняются отдельными сообщениями. Статус подписи DLL и подписи драйвера показывается как наблюдение, без автоматического диагноза. Сборщик не меняет политики Windows и не выгружает чужие драйверы.

## Проверка патча

DLM 0.133.0: восемь наборов тестов, включая прежние режимы, выполнены на Linux с AddressSanitizer и UndefinedBehaviorSanitizer; проверка утечек здесь не выполнялась. Пройдены шесть наборов PowerShell-тестов: Telegram, интеграция подбора, активная сеть, списки CDN, MWO и ошибки драйвера. Они проверяют отмену контроллера, сохранение профиля, атрибуцию по сеансу/сокету, режим без сети, выбор Azure Frontend / AWS GLOBAL и отклонение повреждённых списков.

Четыре приложения проверяются компиляцией и линковкой для Windows x64. Размеры и смещения TCP IPv4/IPv6 таблиц проверены по Windows-заголовкам. Здесь не выполнялись Windows-драйвер, GUI, реальная авторизация MWO и проверка российского подключения. Build-And-Run.cmd повторяет тесты и собирает программы вашим MinGW GCC на компьютере пользователя. В архив входят исходники и скрипты, а не проверочные EXE.
