# Патч 2.3: Telegram Web и Desktop

Обновление исходников поверх DPI DLM 2.2. Готовых EXE в архиве нет.
Скопируйте содержимое `DPI` в `M:\users\Ark\Desktop\DLM\DPI` с заменой,
закройте NoDPI/GUI и запустите прежний `Build-And-Run.cmd`.
Изменённый `Build.ps1` собирает четыре приложения на DLM 0.133.0+.
Нужен прежний x64 MinGW GCC из SDK. Драйвер и config.ini не заменяются.

## Первый запуск

1. Отключите VPN и другие DPI-движки для сравнения. Нажмите «Включить».
2. Полностью закройте Telegram Desktop из трея и снова запустите его.
   Откройте или перезагрузите `https://web.telegram.org/a/` и `/k/`.
3. Проверьте отправку сообщения и загрузку файла. Программа не меняет
   настройки прокси Telegram. Для проверки прямого соединения ранее
   настроенный недоступный прокси в Telegram нужно выключить самостоятельно.
4. При необходимости выберите **Telegram Web + Desktop** в списке сервиса
   и нажмите **«Обучать 10 минут»**. Технические настройки подбираются автоматически.
5. После найденного улучшения нажмите «Включить» и снова перезапустите
   Telegram. Доступны сохранение и загрузка `.profile`.

Достаточно обычного включения, чтобы новые обработчики начали работать.
Подбор нужен, если автоматический вариант не помогает. Существующие
TCP-соединения Desktop не перенастраиваются: требуется новый SYN.
В `media-url.txt` ничего для Telegram добавлять не нужно — это файл
прямого URL видеопотока YouTube.

## Что изменено в обработке

- TLS/SNI-обработка Web охватывает `telegram.org` с поддоменами,
  `t.me`, `telegram.me`, `telegram-cdn.org`. Проверка границ домена
  исключает совпадения вроде `telegram.org.example.com`.
- Отдельный путь для MTProto TCP без SNI: область задаётся официальным
  списком IPv4/IPv6 `data/telegram-cidr.txt`, снимок от 19.11.2026.
  В фильтр добавлен TCP 5222; TCP 80/443 поддерживались ранее.
- Для начальных данных выбирается обычное TCP-разбиение, обратная отправка
  сегментов или перекрытие одинаковыми байтами. Варианты разрезов для
  Desktop ограничены первыми 512 байтами, шестью начальными пакетами
  и тремя секундами от SYN. Крупный пакет больше 4096 байт пропускается.
  После первых данных сервера обработка этого MTProto-потока прекращается.
- Содержимое потока, шифрование и авторизация Telegram не меняются.
  В обработчике Desktop нет fake TLS, RST, модификации ключей или содержимого
  сообщения. Распознавание случайного заголовка помечается только как
  `obfuscated_candidate`; за расшифровку MTProto это не выдаётся.
- Частные/локальные адреса и IP-исключения не обрабатываются. При наличии
  доменных include/exclude-списков бинарный путь отключается, поскольку
  проверить доменное правило для зашифрованного MTProto невозможно.
  Если официальный CIDR-файл отсутствует или не содержит пригодных сетей,
  выключается только бинарный путь; в NoDPI.log будет причина.
- Отключение бинарного пути без удаления файлов: `TelegramEnabled=false`
  в секции `[NoDPI]` либо консольный `--no-telegram`. TLS-обработчик Web
  продолжает действовать. CLI `--telegram` включает бинарный путь обратно.

## Пробы и подбор

Проверяется не только открытие HTML. DLM-код `dpi/mtproto.dlm` формирует
публичный `req_pq_multi` и проверяет `resPQ`: тип, длину сообщения,
совпадение случайного nonce и структуру TL-вектора ключевых отпечатков.
Обмен прекращается на этом этапе: факторизация pq, создание ключа,
вход в аккаунт, API ID, SMS-код и чтение `tdata` не нужны.

PowerShell организует TCP/WSS-соединения и AES-256-CTR обфускацию своего
диагностического запроса через .NET. Движок обработки, параметры, генетические
операции и проверка MTProto-сообщения остаются на DLM. Новых зависимостей
для сборки не добавлено.

При Target=3 один раунд содержит восемь целевых проб:

| Пробы | Количество | Значение |
| --- | ---: | --- |
| Web A/K по HTTP/2 и HTTP/1.1 | 4 | Получение страниц через Schannel |
| WSS с обфускацией, DC1/DC2 | 2 | Публичный ответ MTProto через WebSocket |
| Обфусцированный TCP, DC1/DC2 | 2 | Публичный ответ MTProto через прямой TCP |

Сохраняются проверки контрольных сайтов до подбора и при каждом кандидате.
Есть исходный контроль без NoDPI и отдельный повторный запуск кандидата.
Успех метода засчитывается только при наблюдавшемся преобразовании
успешной целевой пробы: проверяются PID, метка попытки, IP и локальный
TCP-порт. Одного SYN-ACK или HTML недостаточно для объявления работы MTProto.
При ответе 429 подбор останавливается, чтобы не повторять запросы.

В GUI отображаются отдельные счётчики TG Web и Desktop, число кандидатов,
таймер и общий результат проб. Статус «подтверждено» относится к этим пробам
и сравнению с контролем. `resPQ` не является проверкой личности сервера
на уровне полного обмена ключами, входа в аккаунт, доставки сообщения,
медиа или звонков. Их необходимо проверить в приложениях.

Профили Schema=1 совместимы с прежними Target: 0 YouTube, 1 Discord,
2 YouTube+Discord. Добавлены 3 Telegram и 4 все сервисы. Профиль влияет
на свою группу; остальные сервисы сохраняют автоматический подбор и
повторные TCP-попытки. Исправлено прежнее принудительное пропускание
остальных групп при активном профиле. Неподтверждённый кандидат не заменяет
активный профиль; перед заменой остаётся `active.profile.previous`.

## Отчёт при проблеме

При работающем NoDPI нажмите «Проверить сервис» с выбранным Telegram
или запустите **Check-Telegram.cmd**. Расширенная проверка охватывает
DC1–DC5 по TCP/WSS и plain abridged на TCP 5222. Быстрая —
`Check-Telegram.cmd -Quick` — использует DC1/DC2 по TCP/WSS.
Состояние движка не переключается. Нет автоматического входа в аккаунт.

Отчёты: `logs/telegram-check-*.json`, `logs/probe-telegram-*.json`,
`logs/telegram-training-*.json`, `logs/training.status` и JSONL движка.
В них есть этап (connect/send/await/verify), DC/транспорт, задержка,
ошибка и результат проверки. Для TCP сохраняются IP и локальный порт.
События движка: `telegram_transport`, `telegram_tcp_transform`,
`telegram_server_data`, обычные timeout/reset/outcome.
Временные бинарные запросы/ответы удаляются; в журнал они не записываются.
Переписка, ключи аккаунта, tdata, cookies и пароли не собираются.

Затем **«Собрать отчёт» / Collect-Diagnostics.cmd**. В архив включаются
новые отчёты и используемый CIDR-файл. В MANUAL_RESULTS.txt укажите отдельно:
Web A/K, сообщения Desktop, загрузку медиа и звонки.

## Проверка разработки и ограничения

Выполнены тесты DLM с AddressSanitizer/UndefinedBehaviorSanitizer:
область доменов/IP, IPv4/IPv6, восстановление точных байтов TCP при
переполнении sequence, перекрытия, обход исключений, остановка после
ответа/лимитов, совместимость профилей и строгий парсер resPQ.
Повторно проверены прежние core/adaptive/automatic/evolution/capture.
Проверены отдельно отправленный однобайтный abridged-маркер и разорванный
обфусцированный заголовок.
LeakSanitizer в этой среде не поддерживается из-за ptrace, проверка утечек
этим инструментом не заявляется.

PowerShell: парсинг всех скриптов, вектор NIST AES-256-CTR, продолжение
счётчика на границах блоков, направления обфускации, ограничения framing,
отмена, подсчёт проб, атрибуция и сохранность активного профиля.
Локальный TCP-сервер проверил полный диагностический обмен с DLM-кодеком:
abridged/обфускация, ответ по 3 байта за чтение, неверный nonce, -429
и оборванный ответ. Все пять случаев пройдены.
Для всех четырёх Windows-программ сгенерирован C и выполнена компиляция
в объекты x86_64 Windows. Сам GUI и WinDivert здесь под Windows не запускались.
Фактическая доступность у вашего провайдера пока не проверена.

Это локальная обработка TCP. Она не создаёт внешний маршрут и не обещает
устранение блокировки IP/маршрута. Также патч не реализует обход ограничений
Telegram-звонков по UDP и не меняет DNS, маршруты или системный прокси Windows.
