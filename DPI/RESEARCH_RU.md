## Разные причины похожих отказов

Руководство zapret рассматривает не только анализ ClientHello, но и реакцию DPI
на ответ сервера. При анализе серверной стороны предлагается ограниченное
воздействие на TCP receive window. При этом подчёркивается потеря скорости,
если продолжать ограничение после критической фазы. В нашей реализации window
scale сохраняется, сокращение времени ограничено, а вне подходящей области
применения оно не включается. Это кандидат для испытания, не универсальный режим.

Источник: [zapret2 manual, wssize](https://github.com/bol-van/zapret2/blob/3bae3d26d741a8f6e0bc4ea651656b4e1a438375/docs/manual.md#wssize).

Исходные обсуждения октября–ноября описывают случаи, когда страница YouTube
доступна, а видео останавливается. В других наблюдениях поведение различается
между CDN-адресами, транспортами и TLS-стеками. Эти сообщения дают гипотезы для
проверки, но не позволяют определить причину отказа у Антона без его трассы.
Поэтому HTTP status, объём передачи, видеопоток и голос выделены как разные
результаты. Наличие ответа ServerHello само по себе успехом не называется.

Источники: [Flowseal #18271, с 21.10.2026](https://github.com/Flowseal/zapret-discord-youtube/issues/18271),
[zapret2 discussion #340, октябрь–ноябрь](https://github.com/bol-van/zapret2/discussions/340),
[zapret2 discussion #327, наблюдения от 15.10.2026](https://github.com/bol-van/zapret2/discussions/327).

Там же обсуждается зависание посреди TLS record. Автоматический RST помогает
только некоторым приложениям с повторами запросов. Версия 2.0 фиксирует такое
подозрение, но не сбрасывает соединение по одному таймеру. Утрата порядка пакетов
отключает достоверность анализа границ record. Простой keep-alive на границе
record не классифицируется как такой stall.

Источник: [первичное описание и ограничения stallbreak](https://github.com/bol-van/zapret2/discussions/327).

## Математика и сохранение TCP-потока

Для выбора используется оценка по формуле верхней границы Уилсона со
сглаживанием и штрафами за занятость/задержку. Для количества наблюдаемых успехов
s и отказов f:

$$n=s+f+2,\quad p=(s+1)/n,\quad z=1.2815515655446004,$$

$$score=\frac{p+z^2/(2n)+z\sqrt{p(1-p)/n+z^2/(4n^2)}}{1+z^2/n}
-0.04\,inflight-0.000002\,latency_{ms}.$$

Ещё не испытанные кандидаты сначала исследуются по очереди. Статистика ведётся
для конкретного destination IP/port/interface, после 64 исходов старые счётчики
ослабляются. Неопределённые исходы не засчитываются как отказ. Это инженерная
эвристика для меняющейся сети; её оценки не являются гарантированными
вероятностями обхода. В качестве «положительного» события движок видит
транспортный прогресс. HTTP-проба и ручное воспроизведение проверяют другой,
более высокий уровень результата.

Реальные сегменты перекрываются только одинаковыми исходными байтами. Они
не используют несовпадающие данные, зависящие от политики first-wins/last-wins
сервера. Для cover-пакетов независимо обеспечивается старый sequence;
вариант checksum дополнительно имеет неверную TCP checksum. В MD5-варианте
не полагаемся только на поддержку TCP MD5 сервером. Для последовательностей
явно применяется арифметика modulo 2^32. Оригинальный ClientHello не получает
добавочных record headers и не требует подмены последующих ACK/SACK.

Основание для TCP-инвариантов: [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html).
Практические техники и их ограничения: [zapret2 manual](https://github.com/bol-van/zapret2/blob/3bae3d26d741a8f6e0bc4ea651656b4e1a438375/docs/manual.md).

## Почему нужны разные проверки

Discord использует HTTP и Gateway/WebSocket; голосовая часть имеет собственный
сетевой обмен. Ответ публичного Gateway API не доказывает успешный голосовой
звонок. NoDPIProbe не получает токен пользователя и не выполняет вход.

Источник: [официальная документация Gateway](https://docs.discord.com/developers/events/gateway).

Проба WinHTTP сохраняет peer IP и local port, позволяя сопоставить запрос с
журналом движка. HTTP/1.1 и HTTP/2 отражаются по фактически выбранному протоколу.
Браузер может использовать иной ClientHello, ECH, QUIC, прокси или расширения,
поэтому полученный результат не переносится на него автоматически.

Источник ABI: [WINHTTP_CONNECTION_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winhttp/ns-winhttp-winhttp_connection_info).

Если проблема связана с недоступностью маршрута/IP, DNS, VPN-конфликтом,
авторизацией или ограничением самого сервиса, одних преобразований пакетов
может оказаться недостаточно. Это рабочие гипотезы, которые журнал должен
разделить. Проверка в сети пользователя нужна до утверждения об эффективности.
