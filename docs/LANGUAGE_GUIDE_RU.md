# DLM — руководство по языку (Русский)

[English](LANGUAGE_GUIDE_EN.md) · [Главная](../README.md) · [Каталог документации](README.md)

> **Версия исходников: 0.131.0.** Это руководство описывает подтверждённые исходниками и существующей документацией возможности. DLM — экспериментальный язык общего назначения с математическим/доказательным слоем и нативной компиляцией поддерживаемых конструкций. Он **не** является завершённой заменой Rust, C++ или Lean. Возможность, описанная в плане, не считается реализованной.

## 1. Идея и архитектура

DLM соединяет исполняемые программы, математические утверждения и явные сведения об обосновании результата. **Паспорт** логического объекта описывает его происхождение (*provenance*), уровень доверия (*trust*), возможности (*capabilities*), контекст теории и историю вывода. Из паспорта нельзя автоматически сделать доказательство: предположения, аксиомы и внешние данные остаются помеченными.

Слои разделены: исходный код → синтаксический анализ и проверка → типизированные сведения и исполняемый IR → C → нативный исполняемый файл. Доказательные утверждения не исполняются в горячем машинном коде; это **не** означает, что весь итоговый машинный код формально верифицирован. См. [семантику](SEMANTICS.md), [компилятор](COMPILER.md), [законы](DLM_ARCHITECTURAL_LAWS.md), [фактическое состояние законов](LAW_STATUS.md).

## 2. Начало работы

Для сборки самого компилятора нужен Rust/Cargo. Для `dlm build` нужен поддерживаемый 64-битный компилятор C (GCC/Clang на Linux; MinGW-w64 на Windows, не MSVC). Из корня репозитория:

```sh
cargo build --release -p dlm_cli
cargo run --release -p dlm_cli -- --version
cargo run --release -p dlm_cli -- check examples/valid/ordinary_functions.dlm
cargo run --release -p dlm_cli -- run examples/valid/word_count.dlm
cargo run --release -p dlm_cli -- build examples/valid/word_count.dlm -o word_count
cargo test --workspace
```

Если исполняемый `dlm` уже находится в `PATH`, команды сокращаются до `dlm check ...`, `dlm run ...`, `dlm build ...`. Проверка (`check`) не равнозначна запуску (`run`) или компиляции (`build`): исследовательские конструкции могут проверяться, но не поддерживаться нативным backend. Для Windows предусмотрен [скрипт сборки](../tools/build_windows.ps1).

## 3. Первая программа

Создайте `hello.dlm`:

```dlm
module demo.hello

theory Hello {
    fn main() -> Nat =
        let _ = print_line("Hello from DLM!") in
        0
}
```

Запуск: `dlm run hello.dlm`. Нативная сборка: `dlm build hello.dlm -o hello` (на Windows можно указать `hello.exe`). Точка входа `fn main()` вызывается после элементов корневой теории. Возвращаемый `Nat` используется как код завершения в документированных пределах. См. [готовый CLI-пример](../examples/valid/word_count.dlm).

## 4. Модули, функции и управление потоком

В начале файла указывается `module`; `import` подключает другую теорию/модуль. Объявления группируются внутри `theory`, возможны `extends`. Функции пишутся как `fn имя(аргумент: Тип) -> Тип = выражение`. Локальное связывание — `let x = значение in выражение`.

```dlm
module demo.arithmetic

theory Arithmetic {
    fn square(n: Nat) -> Nat = mul(n, n)
    fn capped(n: Nat) -> Nat = if_then_else(n > 10, 10, n)
    let value = square(12)
    print_decimal(capped(value))
}
```

Условия `if_then_else` ленивы (вычисляется только выбранная ветвь); аргументы вычисляются слева направо. Поддерживаются `match`, сопоставление образцов, `enum`, записи `record`, функции-значения и замыкания. Для рекурсии с доказуемым убыванием используется `decreasing`; отдельная форма `loop` задаёт хвостовую потенциально бесконечную итерацию. См. [функции](../examples/valid/ordinary_functions.dlm), [записи и суммы](../examples/valid/ordinary_records_sums.dlm), [циклы и enum](APPS.md).

## 5. Типы, контейнеры и обобщения

Базовые исполняемые типы: `Nat`, `Int`, `Bool`, `Text`. Есть `Option<T>`, `Result<T,E>`, `List<T>`, `Sequence<T>`, `Product<A,B>`, `Sum<A,B>`, записи и перечисления. `Nat` и `Int` математически интерпретируются как целые, но при исполнении ограничены `u128`/`i128`: переполнение — **ошибка**, не бесконечная точность. `Text` хранит UTF-8; индексы текстовых операций не следует путать с байтовыми смещениями.

Пример коллекций:

```dlm
let xs = list(1, 2, 3, 4)
let doubled = map(xs, fun(x: Nat, x + x))
let sum = fold(doubled, 0, fun(acc: Nat, x: Nat, acc + x))
print_decimal(sum)
```

Доступны параметризованные функции `fn identity<T>(x: T) -> T = x`, вывод параметров, ограничения `Eq`/`Ord`, классы типов, специализация, `Fn` и `FnEffect` (с ограничениями). Обычные списки **не** тождественны плотным SIMD-массивам; стоимость операций зависит от представления. См. [обобщения](GENERICS.md), [коллекции](../examples/valid/ordinary_collections.dlm), [числовую семантику](SEMANTICS.md).

## 6. Эффекты, ввод-вывод и ресурсы

Побочные действия описываются контрактами: `Stdout`, `Stdin`, `Args`, `File`, `Net`, `Process`, `Window` и др. Чистый `Fn` не равнозначен эффектному `FnEffect<Bounds,...>`. Ограничения эффекта не дают прав ОС и не создают sandbox.

Файлы поддерживают `file_open`, `file_read_line`, `file_write`, `file_close`, операции над каталогами и атомарную запись; файловый дескриптор линеен: его необходимо закрыть либо передать владельцу. Изменяемые `ByteBuf`/`TextBuf` используют контролируемые `move` и `borrow` правила в поддерживаемой области; это **не** завершённая универсальная модель владения любыми ресурсами. См. [эффектные callbacks](EFFECT_FUNCTIONS.md), [файлы](FILES.md), [владение](OWNERSHIP.md), [файловый пример](../examples/valid/effect_file_transform.dlm).

## 7. Утверждения, доказательства и доверие

```dlm
theorem sum_example: nat_eq(2 + 3, 5)
theorem commutative_small(n: Nat, m: Nat) below 10: nat_eq(n + m, m + n)
axiom assumption(n: Nat): nat_eq(n, n)
conjecture claim(n: Nat) tested 100: nat_eq(n + 0, n)
```

`theorem ... below N` относится **только** к ограниченной области; `conjecture ... tested N` остаётся гипотезой после тестирования; `axiom` остаётся явным допущением. Существуют сертификаты и независимая проверка **ограниченного фрагмента равенств Nat** (C-min); это не полноценный универсальный proof kernel и не доказательство корректности backend. См. [поверхность доказательств](PROOF_SURFACE.md), [проверку равенств](EQUATIONAL_REPLAY.md), [границы доверия](PROOF_CERTIFICATE_AUDIT.md).

## 8. Графика, GPU и научные библиотеки

В проекте есть `std.ui`, `std.vector`, виджеты, программная векторная растеризация, SVG, PNG и интерфейсы окон X11/Win32 в документированной области. В v0.131.0 добавлена **GPU-отрисовка графических сцен через OpenGL** с программным fallback. Это не означает наличие универсального GPU compute backend или автоматического распределения любых вычислений между CPU/GPU. См. [GUI](GUI.md) и [пример интерфейса](../examples/valid/gui_counter.dlm).

Математический раздел содержит **ограниченные** точные вычисления: целые и рациональные числа с явными пределами, матричные алгоритмы, конечную алгебру, гомологии для конечных структур, комплексную арифметику и интервальные методы в отдельных профилях. Универсальность и полнота всех математических теорий не заявляются: [математический прогресс](MATHEMATICS_PROGRESS.md).

## 9. Диагностика и границы гарантий

```sh
dlm contracts examples/valid/integers.dlm
dlm build --emit-ir examples/valid/ordinary_higher_order.dlm -o hof
dlm build --check-overflow examples/valid/integers.dlm -o integers
```

При необходимости `--require-no-overflow` запрещает сборку с незакрытыми машинными обязательствами. Даже успешная математическая теорема сама по себе не доказывает отсутствие переполнения, корректность сторонней библиотеки или безошибочность C-компилятора. На практике стоит сравнивать `dlm run` и нативную сборку и запускать тесты. См. [компилятор](COMPILER.md), [диагностику](DIAGNOSTICS.md), [статус реализации](LAW_STATUS.md) и [план](../ROADMAP.md).
