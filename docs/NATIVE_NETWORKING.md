# Нативная сеть DLM v0.134.0

`std.native_net` предоставляет бинарные TCP/UDP-сокеты и клиентские защищённые
транспорты. `std.native_protocol` — независимые бинарные кодеки. Это рабочие
библиотеки для построения протоколов, а не реализация готового VPN.

## Сборка и установка

Патч накладывается на **DLM(5).zip / v0.133.0**, с сохранением путей `DLM-main/...`.
Изменяется исходный компилятор: при импорте провайдера он включает сетевой C-код
в создаваемый исполняемый файл или библиотеку. Старый `dlm.exe` v0.133.0 не знает
об этом адаптере, поэтому после применения нужен новый компилятор.

Windows: распакуйте архив поверх папки, содержащей `DLM-main` и `DLM-pre`, затем
запустите `DLM-pre/Build-Network.cmd`. Он вызывает существующий сборщик с путями
относительно своего расположения, обновляет SDK и собирает/запускает два примера.
Для сборки используются существующие Rust/WinLibs; первоначальная подготовка
инструментов может потребовать скачивания. Параметр `-SkipCompilerBuild` скрипта
PowerShell предназначен только для уже собранного компилятора >=0.134.0.

На Linux из `DLM-main`:

```bash
cargo build --release --workspace --locked --offline
target/release/dlm build examples/native/network_loopback.dlm --lib lib --allow-unsafe -o network_loopback
./network_loopback
target/release/dlm run examples/native/network_protocol.dlm --lib lib
```

Сетевой модуль выполняется **в скомпилированном native-коде**. Эталонная VM
по-прежнему отвергает произвольные внешние вызовы, а не имитирует соединение.
Чистые кодеки исполняются и в VM, и после компиляции. `--allow-unsafe` явно
разрешает доверенную границу C ABI; это не означает доказательство C-кода.
Форматы обычных `Nat/Int/Text/ByteBuf`, доказательное ядро и прежний `std.net`
не меняются. Новых Cargo-зависимостей нет.

Манифест проекта допускает `unsafe_roots = lib/std/native_net.dlm`: это явное
разрешение только для указанного корневого файла. Строгий режим имеет приоритет.
Аудит показывает native/FFI как Unsafe и перечисляет библиотеку провайдера;
код внешней библиотеки не считается доказанным. Прочие корни проекта сохраняют
прежнюю политику.

## Что поддержано

| Возможность | Реализация |
| --- | --- |
| TCP-клиент и сервер | IPv4/IPv6, nonblocking-сокеты, бинарный поток, accept, write-half-close, TCP_NODELAY |
| UDP-клиент и сервер | IPv4/IPv6, адрес отправителя, отдельные датаграммы, пустые сообщения, признак усечения |
| Ожидание готовности | poll/WSAPoll, один или до 4096 сокетов, монотонное время, отмена |
| TLS-поток клиента | libcurl connect-only, TLS >=1.3, проверка CA/имени, необязательный public-key pin |
| HTTP/HTTPS-клиент | Бинарное тело, явные метод/заголовки, лимиты ответа, информация о версии |
| HTTP/2 и HTTP/3 | Через libcurl с соответствующей сборкой; явные режимы без принятия незапрошенной версии |
| WebSocket/ws/wss-клиент | HTTP Upgrade, заголовки до подключения, бинарные/текстовые фреймы, метаданные фрагментов и управляющих кадров |
| ECH | Явная передача настройки libcurl; экспериментальная возможность backend, не обещание успешного ECH |
| Случайные байты | Системный CSPRNG: BCryptGenRandom или /dev/urandom |
| Кодеки | Big-endian 1–8 байт, QUIC varint, ограниченный length-prefixed framing |

Произвольный QUIC transport, QUIC DATAGRAM API, MASQUE CONNECT-UDP/CONNECT-IP,
TLS-сервер, TUN/Wintun и маршрутизация ОС в этот выпуск не входят. HTTP/3 внутри
HTTP-клиента нельзя выдавать за общий QUIC SDK. Для таких библиотек остаётся
существующая явная граница C ABI.

## Провайдер и его возможности

TCP, UDP, ожидание и системный генератор не требуют libcurl. Для защищённых и
HTTP/WebSocket-клиентов нужен **libcurl >=8.10.0**. Требуемая версия даёт в том
числе определённую семантику ALPN при HTTP/2 prior-knowledge. Наличие DLL само
по себе не гарантирует HTTP/2, HTTP/3, WebSocket, ECH или конкретный TLS backend.
`network_capabilities()` возвращает фактически доступные биты:

| Бит | Значение | Смысл |
| --- | --- | --- |
| 0 | 1 | TCP |
| 1 | 2 | UDP |
| 2 | 4 | Системный CSPRNG |
| 3 | 8 | TLS backend libcurl; успешная TLS 1.3 проверяется при соединении |
| 4 | 16 | HTTP/1.1 через подходящий libcurl |
| 5 | 32 | HTTP/2 backend |
| 6 | 64 | HTTP/3 backend |
| 7 | 128 | API и протокол WebSocket libcurl |

`network_provider_version()` возвращает `0xMMmmpp`, либо 0 при отсутствии
подходящего backend. Возможности означают поддержку локальной сборкой, а не
доступность удалённого сервера или возможность пройти сетевую фильтрацию.

На Windows DLL и её зависимости размещаются рядом с **вашим приложением**.
Ищутся `libcurl-4.dll`, `libcurl.dll`, `curl.dll` через безопасные default DLL
directories, без поиска в текущем каталоге. Можно задать `DLM_LIBCURL` полным
абсолютным путём; зависимости тогда также ищутся в каталоге DLL. SDK из исходного
архива содержит DLL, идентифицирующую себя как libcurl 8.16.0; её возможности
не были подтверждены запуском Windows в этой среде. На Linux используется
системный `libcurl.so.4`, на macOS — системный libcurl; macOS здесь не проверялся.

Инициализация backend выполняется один раз на загруженный native-модуль. Его
библиотечная ссылка удерживается между соединениями. Перед выгрузкой модуля
хост останавливает все внешние вызовы/потоки, закрывает владельцев и вызывает
`unsafe network_provider_shutdown()`. Операция откажет при живых ресурсах,
освободит ссылки на backend и допускает последующую инициализацию. Она не
должна конкурировать с другими вызовами и не вызывается из Windows DllMain.

## Владение, статусы и двоичный ввод-вывод

Сокеты и HTTP-запросы имеют тип `Resource<NetOpened,net_dispose>`. Владелец
перемещается явно и закрывается автоматически при выходе из области, включая
runtime error. Состояние создания читается через `socket_status` и
`socket_system_error`; последующие операции возвращают свой `NetIo`.
Для динамически сформированных имён, URL, путей CA, pin и заголовков есть
варианты `*_bytes`, принимающие `Slice<U8>`: например http_client_bytes и
socket_tcp_bytes. Они не требуют превращать конфигурацию в строковый литерал.

Сначала проверяйте статус создания. Даже неуспешное создание даёт безопасно
закрываемый ресурс с null handle; это не рабочий сокет.

| status | Значение |
| --- | --- |
| 0 | Успех |
| 1 | Сейчас нет данных/места: would-block |
| 2 | EOF потока / конец списка разрешённых адресов |
| 3 | Истёк таймаут |
| 4 | Неверный аргумент, тип операции или состояние |
| 5 | Ошибка ОС, DNS или провайдера |
| 6 | Backend/возможность недоступны |
| 7 | Превышен лимит |
| 8 | Ошибка TLS, доверия, имени или pin |
| 9 | Отмена |
| 10 | Датаграмма усечена: это не успешный полный пакет |
| 11 | Несоответствие протоколу |

`NetIo.count` — реально обработанные байты, в том числе перед EOF, отменой
или ошибкой. `system` — код ОС/DNS либо CURLcode для curl-операции; домен кода
определяется вызванной операцией. Текст или двоичные данные автоматически не
декодируются. Сокетный receive пишет только в предоставленный буфер и не
меняет его длину; значимы только первые `count` байт.

`socket_read` и `socket_write` делают одну неблокирующую операцию; запись может
быть частичной. `socket_read_exact` и `socket_write_all` продолжают работу с
одним общим deadline и возвращают частичный count при неуспехе. Их timeout=0
разрешает только немедленно доступный прогресс. Перед повтором учитывайте уже
обработанный count: автоматическое повторение целого сообщения может дублировать
данные. Пустая запись допустима; socket_read с пустым буфером — status 4.
read_exact/write_all для нулевой длины на действительном потоке завершаются
немедленно с count=0; неверный handle остаётся ошибкой и в этом случае.
TCP EOF не означает завершение сообщения прикладного протокола. Неожиданный
обрыв TLS не преобразуется в успешное завершение защищённого потока.

`socket_tcp(host,port,timeout_ms)` требует ненулевые port и timeout. Синхронное
системное DNS-разрешение выполняется **до** общего connect deadline. Каждый
адрес использует остаток общего бюджета; это не обещание таймаута DNS.
`network_resolve(host,port,index)` возвращает IPv4/IPv6-адрес по индексу. DNS
вызовы блокируют и не обещают cancellation. Для собственного DNS/DoH можно
использовать UDP/HTTPS-клиент и кодеки.

`socket_listen(host,port,backlog)` требует backlog 1..65535; port=0 выбирает
свободный порт. `socket_local` возвращает семейство 4/6, порт, IPv6 scope и
байты адреса. `socket_accept` возвращает status 1, если очередь пока пуста.
`socket_shutdown_write` поддержан для обычного TCP: не делает небезопасный
низкоуровневый shutdown под состоянием TLS.

UDP сохраняет границы сообщений. Пакет нулевой длины имеет status=0,count=0,
а не EOF. Переносимый предел отправки — 65507 байт. Усечённая датаграмма
потребляется целиком и получает status=10; следующий receive читает уже
следующий пакет. TCP/UDP самостоятельно не обеспечивают шифрование.

## Ожидание и отмена

`socket_wait(socket,events,timeout,cancel)` использует READ=1, WRITE=2.
При успехе count содержит readiness bits: READ=1, WRITE=2, ERROR=4, HUP=8.
После ERROR/HUP прочитайте результат I/O: это не обещание успешной операции.
Нулевой timeout — немедленная проверка. Для TLS/WebSocket сначала вызывайте
read, а после would-block ожидайте readiness: внутри libcurl могут находиться
уже расшифрованные данные, не видимые обычному poll ОС.

`network_cancel()` создаёт владельца токена. Проверяйте `network_cancel_valid`:
нехватка памяти не должна незаметно отключить необходимую отмену.
`network_cancel_signal` выставляет флаг, reset используется после завершения
предыдущих операций. Низкоуровневый C signal потокобезопасен; хост гарантирует,
что токен живёт до возврата всех использующих его потоков. Ожидание poll
проверяет отмену не реже чем через 50 мс плюс задержка планировщика ОС.
HTTP perform использует progress callback libcurl: такой же предел задержки
отмены для DNS/TLS/HTTP не обещается. TLS/WebSocket setup пока синхронен и
ограничен таймаутом libcurl, без отдельного cancel-параметра.

`socket_poll_entry` / `socket_poll` остаются явно unsafe: записи содержат
заимствованные foreign handles, а существующая модель DLM не кодирует их
время жизни в записях. Храните всех владельцев живыми, не закрывайте и не
используйте тот же socket повторно до завершения poll. Максимум 4096 записей.
Высокоуровневый socket_wait заимствует одного владельца на время вызова.

## HTTPS, HTTP/2, HTTP/3 и ECH

`http_client(url,timeout_ms,maximum,ca_file,pin)` создаёт запрос, но не выполняет
его. Поддержаны только http/https. Лимит тела 1..64 MiB, заголовков ответа —
64 KiB. Переполнение callback-лимита — status 7, включая неизвестную заранее
длину тела. Это API буферизует ограниченный ответ, а не предоставляет HTTP
streaming API. Таймаут libcurl — 1..2147483647 мс.

`http_body` копирует бинарный вход до возврата, `http_method` задаёт метод,
`http_header` добавляет явный заголовок без CR/LF/NUL. Заголовок запроса — до
8192 байт. Проверяйте результат каждой настройки. `http_version`: 0 — выбор
backend, 1 — HTTP/1.1, 2 — HTTP/2 prior-knowledge, 3 — HTTP/3-only.
Неподдерживаемая локальная версия возвращает status 6. После передачи проверяется
фактически выбранная версия; несовпадение даёт status 11. Проверка ответа не
отменяет уже произошедшие действия сервера: библиотека сама не повторяет запрос.

`http_perform` возвращает число принятых байт и статус транспорта. HTTP 404/500
не превращаются в транспортный отказ: код ответа читается через http_info.
Поля http_info: 0 — HTTP status, 1 — версия (1/2/3), 2 — длина тела, 3 — длина
заголовков. `http_read(request,headers,offset,buffer)` копирует сохранённые байты.
После ошибки частично принятый ответ доступен, но не считается завершённым.

Проверка CA и имени всегда включена, TLS минимум 1.3. Пустой ca_file использует
настройку доверия backend; непустой — явный файл CA. Пустой pin отключает только
дополнительное закрепление ключа, не проверку сертификата. Pin использует формат
libcurl, например `sha256//BASE64_SPKI_HASH`. Redirect и прокси из переменных
окружения автоматически не включаются; автоматических повторов запроса нет.
TLS-поток `socket_tls` использует https URL для настройки TLS с ALPN HTTP/1.1,
после чего передаёт произвольные байты без выполнения HTTP-запроса. Это не API
произвольного выбора ALPN/настройки TLS-server.

`http_ech` передаёт явную настройку CURLOPT_ECH: например `hard` требует ECH,
тогда как `true` допускает его отсутствие. Поддержка зависит от TLS/DNS backend;
опция остаётся экспериментальной у libcurl. Успех setopt не является свидетельством
успешного ECH-рукопожатия. Патч не обещает обход блокировок или необнаружимость.

## WebSocket

Создайте websocket_client, добавьте аутентификационные заголовки через
http_header и вызовите websocket_start. Клиентские кадры маскирует libcurl.
websocket_write отправляет один фрейм; flags: TEXT=1, BINARY=2, CONT=4 (сообщение
продолжится следующим фреймом), CLOSE=8, PING=16, PONG=64. Управляющий фрейм
не фрагментируется и не длиннее 125 байт. Данные не длиннее 64 MiB за вызов.
Незавершённая отправка по ошибке/таймауту делает соединение непригодным для
продолжения: закройте владельца, учитывая возможную доставку части сообщения.

websocket_read возвращает count/status, флаги, offset внутри текущего фрейма
и remaining. Получение части фрейма не завершает ни фрейм, ни всё сообщение.
Собирайте фрагменты с собственным общим лимитом и обрабатывайте control frames
между ними. Автоматическое поведение PING/PONG — стандартное поведение libcurl.
API не выдаёт целое сообщение за одну порцию и не хранит бесконечную очередь.

## Кодеки и независимые проверки

protocol_read_be / protocol_write_be принимают ширину 1..8, проверяют границы
до доступа и не обрезают переполненное значение молча. quic_varint_read/write
соответствуют RFC 9000 section 16: предел 2^62-1, длина 1/2/4/8. Стандарт
допускает не минимальную форму при чтении; запись использует минимальную.
protocol_frame32 читает U32 big-endian длину без выделения памяти из удалённого
поля. Недостающий ввод — 1, неправильный offset — 4, превышенный максимум — 7.

```bash
cargo test --release -p dlm_core --test native_network
python3 crates/dlm_core/tests/native_hosts/network.py
```

Python-тесты используют независимые локальные TCP/UDP/TLS/HTTP/WebSocket peers;
для сертификатов нужен OpenSSL CLI, для проверки HTTP/2 — Node http2. Для
обязательной проверки backend задайте DLM_NETWORK_REQUIRE_CURL=1. Пакет без
curl продолжает обслуживать обычные TCP/UDP; отсутствующие расширения выдаются
явным статусом, а не мнимым успехом. Результаты конкретного прогона перечислены
в NATIVE_NETWORK_TEST_RESULTS.md.
